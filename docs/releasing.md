# Automatic PIE releases

The alpha channel starts at **0.1.0-alpha.1**. Fixes and features increment the alpha counter; breaking changes advance the minor base and restart at alpha.1. Maintenance-only commits do not release. Stable promotion requires a reviewed channel change. Only release tags reachable from the candidate commit affect version selection.

Run `npm ci --ignore-scripts`, `node --test scripts/release-tools.test.mjs`, and `npm run release:plan --silent` in a Git checkout. Planning is read-only. `python3 scripts/prepare-release.py VERSION` requires a clean checkout and prepares the workspace version, both lockfile package entries, and changelog together. Commit summaries are generated from Conventional Commits; existing Unreleased notes move into the new version. The ledger transition validator may update only the two Cargo dependency hashes after proving the restricted version-only change described below; native proof contents are never rewritten.

## Default-token release flow

The `automatic-alpha-release` workflow uses the short-lived default GITHUB_TOKEN with contents, pull-request, and actions write permissions. No personal access token, private key, Packagist API token, or external publishing secret is required. The repository must allow Actions to create pull requests. Main protection must require the stable `quality-gate` check, enforce up-to-date branches, and permit squash merging without bypassing checks.

After complete quality validation of current main, the workflow prepares a version candidate PR. GITHUB_TOKEN changes do not trigger ordinary push/PR workflows, so automation explicitly dispatches `ci.yml` on the candidate branch with an `expected_sha` input. CI verifies this source pin before other work. Candidate branches include their base SHA and are reused on retries.

On successful candidate quality completion, orchestration checks the branch head, bot PR author, unchanged main base, exact metadata-only file set, version-only manifest change, unchanged dependency graph, and independently derived two-hash ledger transition. It uses a protected squash merge with an exact head-match condition. It then explicitly dispatches the full quality workflow on the merged main SHA. No publication occurs from a candidate branch or solely from PR checks.

Privileged orchestration checks out trusted main, never candidate scripts. Candidate commits are inspected through immutable Git objects. Only same-repository bot-dispatched release branch runs are eligible; fork runs, unrelated actors, changed heads, and stale bases are refused. Races after dispatch are caught by the CI expected-SHA preflight or publication head verification.

## Restricted version transition

`scripts/validate-version-transition.py BASE_SHA VERSION --apply` derives a ledger update from immutable base bytes. Before changing anything it requires the exact 25-input dependency inventory and verifies every base dependency hash. It proves that only workspace package version text and the two internal Cargo.lock package versions changed; editions, dependency versions, lock text outside those entries, build.rs, build flags represented by audited inputs, runtime sources, fixtures, and all other proof dependencies remain identical.

Only the Cargo.toml and Cargo.lock dependency SHA-256 values may change. Source spans, replacements, native compiler/libc contexts, equivalent classifications, and every other ledger byte remain unchanged. Missing/stale hashes, changed native contexts, extra lock entries, source edits and arbitrary ledger edits are rejected. The receipt at `target/version-transition.json` records the base SHA, actual old/new hashes, ledger hashes and unchanged-input count. It is evidence of a version transition, not a replacement for native validation.

Preparation applies this helper before committing. Trusted-main orchestration independently derives the expected ledger from base and candidate Git objects, then requires exact candidate ledger bytes; candidate helper code is never trusted. Fresh NTS and ZTS native compilation context checks and full Mull runs still gate the candidate. No coverage, mutation score, or equivalent classification threshold is weakened. The Rust-visible report version intentionally changes; no C proof is generalized to a changed build script or registry dependency graph.

## Source archives and publication

PIE uses Packagist package `janalis/php-profiler`, composer.json and packaging/config.m4. Installation requires Rust and matching PHP development headers. `python3 scripts/package-source.py` produces `target/php-profiler-source.tar.gz` from clean committed HEAD with reproducible metadata and committed export rules.

`PUBLISHING_ENABLED=true` enables publication only after exact main quality validation. Finalization independently verifies the successful main quality run, current main head, clean tracked checkout, committed workspace version, and complete source archive contents. Historical evidence cannot approve a changed tree. A version transition still fails if the base native ledger is stale, including after source formatting. Such a base requires a separate audited proof renewal; the release helper cannot renew it. Unsupported allocation measurements, measured disabled overhead and upstream failed-startup sanitizer limitations remain documented; alpha publication does not establish production readiness.

The finalizer creates an immutable lightweight version tag using a real non-force Git push, then creates the GitHub prerelease with source archive and SHA-256 checksum. A Git Database create-ref request is deliberately not used: the registered Packagist integration listens for push events. The ephemeral runner configures Git authentication from its short-lived GitHub token, verifies the origin repository, checks any local tag is a lightweight tag for the exact candidate, and rechecks current main immediately before pushing. No credential is placed in a remote URL or printed command argument. Existing remote tags must identify the same source; existing assets must contain identical bytes. Missing assets may be added, but differing assets and tags are never overwritten.

Packagist's GitHub integration must be configured for this repository. After tag/release creation, finalization checks the full package API for the exact version, repository URL and source SHA. Indexing is retried four times at ten-second intervals. A missing or delayed webhook fails visibly while preserving the immutable GitHub release; rerunning the failed release workflow resumes verification. No Packagist credentials are transmitted by the release job.
